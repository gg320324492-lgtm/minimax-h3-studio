## 一、指挥窗口已实测的事实（本指令建立在此之上，不是引述）

### 1. P17 测出的问题（`c284f2f`）

> **「一份 45s、1080p60 的 demo 今天就能写出来（schema 无时长上限），但无法被察觉。」**
> 实测：`--props` 对 **1.0s 的片子、300.0s 的片子、640×480@24 都退出 0**；
> **没有任何生产路径调用 `visual_qa`**；**`render.mjs` 不含任何 QA 调用**；
> `pipeline_manifest.yaml:198-204` 本来就写着「质量门禁（当前全部无自动执行）」/`enforced: false`。

**本项就是那道解药。**

### 2. 但接线有三处硬事实，先看清再动

**(a) `render.mjs` 渲染的是视频，`visual_qa` 的大部分规则要的是 PNG。**
`run_on_frame(frame)` 吃一张帧图。**逐帧解码整部片子成本多少？**
P13 实测：801 帧整片渲染 **约 18.7s**；逐帧解码可能比渲染本身还贵。

**(b) 闸现在有三重非零条件**（`visual_qa.py:1534`）：

```python
return 1 if hard or unver or theme_blocked else 0
```

`hard`（FAIL）｜`unver`（UNVERIFIABLE）｜**`theme_blocked`**（P22 引入）。
⚠️ **`UNAVAILABLE` 不在其中** —— 而 P23 实测 `--frame fr_a/0020.png` 是
`0 FAIL, 2 UNVERIFIABLE, 5 UNAVAILABLE`。

**⇒ 换句话说：拿现在的 `visual_qa` 直接当门禁，任何一次正常渲染都会红** ——
**而那个红不来自这次渲染，来自仪器没建。**
**这正是 P18 记的「永久红的闸」，只是换了个入口。**

**(c) 渲染成功之后才接 QA，那么 QA 红了片子已经产出。**
**这是好事还是坏事，取决于 QA 失败时 `render.mjs` 怎么做** ——
**退出非零会让 CI 拦住，但产物已经在磁盘上。**

### 3. 已有工具：`frame_baseline`（P24）

`studio/scripts/frame_baseline.py`，入口：

```
verdict_profile(findings, drop) -> dict[str, str]
compare(current, baseline, ...) 
read_baseline(path) / write_baseline(path, profile, subject)
```

**它比的是判定，不是数值** —— 因为 P24 实测**判定可复现 1356/1356 = 100%**，
而数值在同一次渲染的两次运行间就能摆动 **96.88%**。

**⇒ 这条现成工具恰好绕开「P13 产物不可复现」**。
