**A** = 从这部片实测得出，附数字与帧号 ｜ **B** = 仍然不能 ｜ **C** = 量到了但口径不同

| # | 维度 | 裁定 | 实测依据（帧号 / 数字） | 为什么不是别的 |

## 3. ⚠️ 底色冲突：分析与建议（**不实施**）

### 3.1 冲突的**前提本身**要改

工单写「参考片 23–48 秒是浅灰底，本项目全部产物是 premium-dark，**要对齐就冲突**」。
实测：**冲突是真的，但边界画错了，而且只在片子的**一半**上成立**。

| | 工单假设 | 实测 |
|---|---|---|
| 参考片底色 | 23–48s 浅灰 `[224,224,224]`，48s 后转深 | **0–23s 暖米**、**23–51s 近白 `[252,252,252]`**、**51–55s 近黑**、**55–67s 白卡片浮深底**、**67–83s 近黑** |
| 与本项目的关系 | 全片都与 premium-dark 冲突 | **67–83s 与 premium-dark 高度同构**（见 §4） |

### 3.2 建议：**只对齐布局，不改主题**（三理由）

1. **本项目的主题不是「深色 vs 浅色」之争，是两套都有的系统。**
   `themes.ts` 已定义 `premium-dark` **与** `premium-light`，且 P6.5 记录了
   为什么「半接线的主题比没有主题更糟」。**改主题会砸掉一个已存在的、已解决的问题。**
2. **近黑段与本项目 token 对得上**（§4）—— 说明 `premium-dark` 不是孤例，
   而是**与参考片某一段同构**。改主题等于扔掉唯一有实测支撑的那部分对齐。
3. **23–51s 那段是数据看板的白底仪表盘**，与本项目的**图表形态**更相关，
   而与主题无关。要吸收的是**卡片栅格、数字层级、表格排布**，不是它的白底。

> **⚠️ 这是建议，不是裁定。** 是否把 `premium-light` 用到某些 scene、
> 或把 KpiHero/DataColumns 的底色改成浅色，**是设计决策，需要人点头**。
> 本项**未改 `tokens.ts` 的任何值**。

## 4. ⚠️ `premium-dark` 有没有参考片背书？——**有，而且是刚刚实测出来的**

P16 的结论是「tokens.ts 那段注释是**规则**不是测量，**没有任何 hex 被追溯到片子**」。
**复核为真**：全仓没有任何一处把 hex 值与片源关联。

**但 P16 的推论「所以 premium-dark 本身也没有背书」需要修正。**
现在片源在手，**可以第一次做这个比对**。实测（68–83s 近黑段，逐帧取样）：

| token（`themes.ts` premium-dark） | 片中最接近的实测色 | ΔRGB | 判断 |
|---|---|---|---|
| `background: #0A0A0C` | `(11,11,11)` @f=4116 | **1.7** | ✅ **吻合** |
| `backgroundAlt: #101014` | `(18,18,20)` | **2.8** | ✅ **吻合** |
| `surface: #141418` | `(19,19,20)` | **4.2** | ✅ **吻合** |
| `surfaceElevated: #1C1C22` | `(34,29,20)` | **15.3** | ⚠️ 偏离（片子的高光层更暖） |
| `ink: #F5F2EA` | `(251,250,248)` @f=4830 | **17.2** | ✅ **接近**（片子的墨更纯白，无暖偏） |
| `accent: #E8C464` | `(243,180,74)` @f=4890 | **31.2** | ⚠️ **偏离最大**：色相 **44°(token) vs 38°(片子)** |

### 4.1 结论（分两句，都要）

1. **「近黑 + 暖白墨」这条设计语言，现在有实测背书了** —— 四个 token 落在
   ΔRGB ≤ 4.2，**这不是巧合能解释的量级**。
2. **但没有一个 hex 是「从片子里量的」** —— `surfaceElevated` 与 `accent`
   明显偏离，且 `accent` 的**色相差 6°**（片子更橙）。
   **`premium-dark` 是「与参考片某一段同构」，不是「由参考片推出」。**

> **⚠️ 这是本次唯一一条把 P16 结论往回拉的话。**
> P16 说「没有背书」——**就「没有可追溯的测量」而言是对的**；
> 但它顺带推出的「所以 dark 是历史遗留」**不成立**：
> 片源显示这套语言**确实对得上参考片的一段**，
> 只是 `accent` 的具体取值与片子有 6° 色相差。

## 5. 守卫：如何在**没有那个 mp4 的机器**上工作

### 5.1 设计（`tests/test_p37_reference_probe_works_without_the_film.py`）

**守卫从不打开片子。** 片源在仓库外（`Documents/…/xwechat_files/`），
任何依赖它的测试都会在没有该文件的机器上变红 —— **那是测「谁装过微信」，
不是测代码。** 四条断言：

| # | 断言 | 挡住的失效 |
|---|---|---|
| 1 | `probe(缺失路径)` 十二维度全 `UNAVAILABLE`，**且不抛异常、且 `reason` 非空** | 探针异常被当成判定（P31/P34 各栽过一次） |
| 2 | **临时合成的片段**（`ffmpeg lavfi` 生成，160×90，2s，落 `tmp_path`）与缺失文件**裁定不同** | 判据不依赖输入 |
| 3 | **两部不同的合成片**（有音轨 / 无音轨）**裁定不同** | 专抓「判据不依赖输入」 |
| 4 | P37 文档的十二维度表**逐行解析**，A 数 > 0 | 散文冒充判定（P16 的老伤） |

### 5.2 校准物为什么不是提交一个 fixture

`.gitignore:2` 是 `*.mp4`，`git ls-files "*.mp4"` **为零**
⇒ **本项目从不跟踪媒体**。提交一个 fixture 会是多年来的第一个例外。
所以**校准片段是现场造的**：`ffmpeg -f lavfi` → `tmp_path`，几 KB，测完即走。

### 5.3 一条额外的硬断言

`test_the_probe_never_reads_the_film_path_itself` **扫描仪器源码**，
断言其中不出现 `Documents` / `xwechat` / `wxid_` / `.mp4`。
**把「守卫不能依赖片源」这件事从约定变成可执行的断言。**

### 5.4 变异结果（实测，`-rf` 原始输出见交付报告）

| 变异 | 期望 | 实测 |
|---|---|---|
| **M1** 缺文件时报 `A`（PASS）而不是 `UNAVAILABLE` | 红 | ✅ **红**（`{'A'} == {'UNAVAILABLE'}`） |
| **M2** `adjudicate` 无视输入、恒返回全 A | 红 | ✅ **红**（`assert 'A' != 'A'`，由 M3 那条断言抓到） |
| **M3** `beat` 对每部片都给同一个答案 | 红 | ✅ **红**（`assert 'A' != 'A'`） |
| **M4** 只改汇总行的 A 数（4→0），十二行不动 | 红 | ⚠️ **第一版存活** → 加了汇总与逐行的交叉校验后 **红** |

> **⚠️ M4 是本项自己踩的第四个坑，也是唯一一个「守卫生病」**：
> 第一版守卫解析了十二行、检查了 `A>0`，但**没有把汇总数与逐行数对照**。
> 于是「只改汇总」这种最像人的编辑手法**穿过去了**（7 passed, exit 0）。
> 补上的断言在失败时**直接报出两边的字典**：
> `the summary tallies {'A': 0, ...} but the twelve verdict rows tally to {'A': 4, ...}`。
> **这正是 P16 那个文件要挡的漂移，在我这里被重新引入了一次。**

### 5.5 守卫的三条硬性质（各自有测试）

1. **缺片 / 无 ffmpeg ⇒ 十二维度全 `UNAVAILABLE`，不抛异常、`reason` 非空。**
   实测：`ffmpeg_available()` 改为 `False` 后对一个**存在的**文件 probe，
   返回 `ffmpeg/ffprobe not on PATH`，十二维度全 `UNAVAILABLE`。
   （⚠️ 第一次验证时我传了一个**不存在的**路径，被 `is_file()` 提前短路，
   **根本没走到 ffmpeg 分支** —— 差点把「测过了」记成假的。换存在的文件重测才作数。）
2. **合成片段 vs 缺失文件 ⇒ 裁定不同**（证明判据读了输入）。
3. **两部不同的合成片（有/无音轨）⇒ 裁定不同**（证明判据分得清不同输入）。
