> 结论先行：**bundle 复用不值得建（B），scene 级重渲现在也不值得建，但原因和
> 工单预期的不一样（C）。** 数字全部来自本机实测，见下。**没有实现任何东西。**

## 1. 一次 bundle 真实耗时：**1.2 – 1.5 秒**

工单说"若渲染太慢跑不动，量到 bundling 阶段就停"。**没有停 —— 全片渲完了**，
所以这里给的是整条流水线的数字，不是半截的。

三次连续全片渲染（同一份 props，`--concurrency 16`，`--crf 23`）：

| 运行 | `bundle done in` | `composition … metadata in` | 总计 |
|---|---|---|---|
| demo1 | **1.2s** | 0.3s | 19.6s |
| demo2 | **1.3s** | 0.3s | 19.8s |
| demo3 | **1.2s** | 0.3s | 19.3s |

另加 concurrency=1 两轮：bundle **1.5s / 1.3s**，总计 56.2s / 55.4s。

**bundle 是总耗时的 6%**（1.2s / 19.6s）。

### 1.1 为什么 800 MB 只需要 1.2 秒

`studio/public` 实测 **773 MB / 127 个文件**。`@remotion/bundler` 的
`copy-dir.js` 是逐文件 `fs.promises.copyFile` —— 127 个 6 MB 的块拷贝，
在 NVMe 上就是 1.2 秒。**拷贝量从来不是问题，文件数才是。**
800 MB 这个数字一直误导人：那是一次顺序大拷，不是 800 MB 的随机写。

> 顺带：`studio/BENCHMARK_20260929.md` 早就写着 `bundle() 1.0s`。本次独立实测
> 1.2–1.5s，与之一致。**这不是我算出来的修辞，是复现了旧基准。**

### 1.2 磁盘事故没有被重演

`render.mjs:43-59` 记录的 118 个副本 / 46 GB：本次 11 次渲染跑完后，
`studio/.remotion/bundle/` 与本次用的 `out/p13_probe/scratch/` **均为空目录**。
`finally` + SIGINT 的清理在真实运行中确实生效。测量用的产物全在
`out/p13_probe/`（gitignored，E: 盘）。**未删除任何既有 bundle 目录或 out/ 目录。**

## 2. 改一个 scene 现在要多久：**19.5 秒 —— 和什么都不改完全一样**

把 `s01_kpi.content.value` 从 7263 改成 9999，重渲：

| | bundle | 总计 |
|---|---|---|
| 原图 | 1.2s | 19.6s |
| **改一个 scene 值** | **1.2s** | **19.5s** |

**一秒之内都看不出来。** 因为 `render.mjs` 没有 `frameRange` / `imageRanges`，
没有 `--scene`，整片永远是全渲。

### 2.1 但"全渲"不等于"没有可省的"—— 这是本项最关键的实测

逐帧像素比对（全分辨率，1920×1080，每 20 帧采样），
`mut-vs-base` 与 `rerun-vs-base`（两次**完全相同** props 的重渲作为噪声底）：

| 帧段 | 改动 scene 的 delta | 同图重渲噪声底 |
|---|---|---|
| 0–229（s01，**被改的 scene**） | **710 – 761** | 0 |
| 240–440（s02，未改） | 3 – 198 | 0 – 224 |
| 480–800（s03/s04，未改） | **0** | 0 |

**scene 局部性是真的**：改一个 scene，效应止于该 scene，delta ~730，
比噪声底高一个数量级；s03/s04 段**逐像素为零**。

> ⚠️ **我第一版把 240–440 段写成"逐像素相同"，那是错的。**
> 那个结论来自 480×270 下采样比对 —— 差异被平均掉了。
> **在错误的尺度上测量，等于什么都没测。**
> 修正后的断言在 `tests/test_p13_scene_cache_facts.py::test_a_scene_change_is_confined_to_that_scene`
> 里对着噪声底比较，不是对着 0，并且把这个错误写进了 docstring。

**所以"渲染器泄漏"不是不建的理由。真正的理由是：没有 scene 级入口可寻址，
而建了入口之后能省多少 —— 见下。**

## 3. 能省多少

单 scene 单独渲（临时把图裁成一个 scene，`resolveShowcaseMeta` 求和）：

| scene | 帧数 | 总计 | 减去 bundle |
|---|---|---|---|
| s01_kpi | 229 | 7.3s | 6.1s |
| s02_dash | 229 | 7.7s | 6.5s |
| s03_columns | 114 | 5.5s / 5.7s（两轮） | 4.3–4.5s |
| s04_calendar | 229 | 7.8s | 6.6s |
| **整片** | **801** | **19.6s** | **18.4s** |

> ⚠️ 我第一批单 scene 循环里 s03 报了 229f/7.2s，**与它 114 帧的声明矛盾**。
> 查下来是我读到了**上一轮的旧日志行**（`run_only2.log` 里 229f 那行来自更早的全片渲染）。
> 单独重跑两次均为 **114f**（`run_only2c.log`），与图谱声明一致。
> **帧数以 ffprobe 独立复核过，不只信 render.mjs 自己打的那行。**

### 3.1 bundle 复用能省的

**每个进程 1.2 秒，封顶。** 而且只在同一个进程渲多次时才能省到 ——
`render.mjs` 每次 `mkdtempSync` 一个新目录并在 `finally` 删掉，
一个进程一次 bundle。**今天的形态下，这个 1.2 秒省不掉，
除非先把 render.mjs 改成长驻进程 —— 那就是 P14。**

### 3.2 scene 级重渲能省的

改了 s01（229/801 帧 = 28.6%）：19.6s → 7.3s，**省 12.3s / 63%**。
改了 s03（114/801 = 14.2%）：19.6s → 5.5s，**省 14.1s / 72%**。

**这个比例是真实的、显著的。** 问题不在收益，在代价。

## 4. 判定

### 4.1 bundle 复用：**B —— 不值得建**

1.2 秒，占单次渲染 6%，**且在当前每次一进程的形态下根本省不掉**。
`job_state.json` + hash 缓存换不回 1.2 秒。
1.2 秒的固定开销要靠**长驻进程**消灭，不是靠缓存 ——
所以它的自然形态是 **P14（Render Worker / Fast Preview）**，
不是 P13。工单第六节已经预留了这个位置，本节给出实测支持。

### 4.2 scene 级重渲：**C —— 现在不建，但理由不是收益小**

收益 63–72%，够大。但三个实测事实挡住了现在动手：

**(a) 产物不可复现，缓存的正确性判据无处落地。**
同一份 props 连渲三次得到三个不同的 mp4：711054 / 710851 / 712303 字节，
三个 sha256 全不同。**不是并发竞争** —— concurrency=1 时同样不可复现
（621942 / 621287），而 `ffmpeg` 对同一输入编码两次是逐字节相同的。
差异极小（最坏 123，集中在某一 scene 的一段），但它是**真实存在**的。
⇒ 「同一份 props 连续渲染两次产物一致」这条性质**今天为假**。
缓存若以 props hash 为键，就不能靠"重渲一遍比对"来验证命中 ——
正确性只能来自"键覆盖了全部输入"，而这一点需要先解决 (c)。

**(b) 现有系统完全察觉不到"改了一个 scene"。**
把 `s01_kpi.content.value` 7263 → 9999，`visual_qa.py` 的报告**逐字节相同**，
退出码相同。唯一读图谱的规则 `missing_asset` 检查的是四个硬编码音频路径，
**没有任何代码比较图谱**。⇒ 增量构建要回答"什么变了"，而现在**没有任何一层**在回答它。
（这不是 QA 的缺陷：QA 是像素门禁，改数字不改变它应用的规则。
但它意味着 P13 要自己建这个能力，而且这才是主要工作量，不是缓存本身。）

**(c) 一半收益会被 re-encode 吃掉。**
省下的是渲 229 帧，不是省下成片。拼回 mp4 要重新编码整条时间轴，
成本没有实测，但它吃掉一部分 63–72%。**我没有实测这一项，
不把它算进收益 —— 上面的 63–72% 是上限。**

**判据明确到可以重新评估**：当 (a) 不可复现被解释或消除、
(b) 有办法算出 scene 级的 diff、(c) re-encode 成本被实测，
P13 就变成一个合理的 C → A。现在建，等于在一个还没有判据的地方先写缓存。

> **瓶颈到底在哪**：不在 bundle（1.2s / 6%），不在场景局部性（存在，且很强），
> **在"没有 scene 级入口"和"没有 scene 级 diff"**。
> 前者是 `render.mjs` 缺一个 `--scene`/`frameRange`，
> 后者是无人比较图谱。两者都不是 `job_state.json` 能解决的。
