## 一、指挥窗口已实测的事实（本指令建立在此之上，不是引述）

### 1. P13 已经把这一项的前提测出来了（`6eca430`）

`docs/P13_CACHE_PAYOFF.md` 的结论：

| 事实 | 数字 |
|---|---|
| **bundle 耗时** | **1.2s / 19.6s = 6%**（三次实测 1.2 / 1.3 / 1.2） |
| **为什么快** | `studio/public` = **127 文件 / 810.6 MB** —— **体积大但文件数只有 127**，bundler 逐文件 `copyFile` |
| **为什么省不掉** | `render.mjs:57` `mkdtempSync` 每进程新建 + `finally`/`SIGINT` 删除 |

**P13 的原话**：bundle 复用要省掉那 1.2s，**必须先变长驻进程**，
而变长驻进程就是 P14。**所以 P14 是 bundle 复用的前提。**

**但请注意这个推理链的脆弱处**：它假设「长驻进程 → 省掉 1.2s」。
**长驻进程本身的成本（常驻内存、bundle 失效的判据、并发安全）没有被任何人测过。**
**那可能比 1.2s 更贵。这是本项要回答的第一个问题。**

### 2. `render.mjs` 现有的清理逻辑不能照搬

`render.mjs:59-73` 的注释记录了原因：

```
// A failure below must not leave an 800 MB directory behind, and neither must
// a Ctrl-C: the exit handler runs on SIGINT, the finally does not.
```

而 `:45-47` 记录了事故本身：

```
// NEVER deletes it (prepareOutDir in @remotion/bundler), so every render leaks
// one copy of studio/public onto the system drive — 118 of them filled a C:
// TEMP to 46 GB.
```

**长驻进程意味着那个 800 MB 目录不再被删 —— 它会一直在。**
**这是把一个"每次泄漏"的问题换成"永久占用"。**
请说清这个交换是好是坏，以及常驻的内存代价是多少。

### 3. 预览粒度的现实：scene 数很少

指挥窗口实测（`pipeline/examples/*.json`）：

| 图谱 | scene 数 | 总帧数 |

| `charts_demo.json` | **10** | 1950 |
| `showcase_demo.json` | **4** | 801 |

**十来个 scene。** 分级渲染（scene/draft/full）的收益上限，
在这么短的成片上可能很小 —— **但请实测，不要估算。**

### 4. 没有 scene 级入口，且产物不可复现（这两条直接限制分级渲染）

- **无 scene 级入口**：`bin/` 只有全片 `render.mjs` / 单帧 `still.mjs`；

## 二、你要交付的三件事

### 第 1 件事：**量长驻进程的真实成本**（不是收益）

**这是本项的核心，也是 P13 没能回答的那一半。**

必须给出**实测数字**：

1. **常驻 bundle 的内存占用**。让一个 bundle 活着，量它的 RSS 或等价指标。
   **用任务管理器数字或进程统计都可以，但要说明怎么量的。**
2. **bundle 何时失效**。改一个 `.tsx` 之后，一个已存在的 bundle 还能用吗？
   Remotion 的 bundler 有 watch 机制 —— **请实测它是否会自动重建**，
   不要假设。若它不自动重建，**长驻进程就需要一套失效判据**，那是本项最大的复杂度来源。
3. **一次全片渲染里的"固定开销 vs 可变开销"分别是多少**。
   （bundle 1.2s 已知；渲染本身呢？`selectComposition` 的 metadata 耗时？）

⚠️ **本项目最贵的一条教训**：**在错误的尺度上测量等于没测**。
上一轮 agent 在 480×270 下采样上测局部性，差异被平均掉，delta 实测 198。
**你的测量尺度要与被测量匹配。**

⚠️ **另一条**：**先证明被测对象存在，再测量**。
本项目测过一次 150 帧场景的**帧 120**（80% 处、生命周期 exit 阶段、图表已退场），
测出来的"墨迹"全是背景噪声。

### 第 2 件事：**判定建不建**，写清依据

必须回答：

> 减去长驻进程的成本后，P14 现在建了**净省多少**？

三档：**A 值得建**（给最小设计，不实现）／**B 不值得建**（记录理由与瓶颈在哪）／
**C 拆开**（例如长驻 bundle 值得但分级渲染不值得，**逐条给结论**）。

**B 和 C 是完全合法的结论。** 本项目已接受 P12 的「零段值得建」与
P13 的「B + C」。**不要为了交差而建。**

**若判 B 或 C，必须同时回答**：**瓶颈到底在哪？**

**请复核这个答案是否也适用于本项**，或给出不同的答案。

### 第 3 件事：给"分级渲染"这件事上一条守卫

无论建不建，**判据先钉住，将来谁建时有东西可依**。

守卫必须落在**可测行为**上，断言**当前系统的真实性质**（不是理想性质）：

- 「当前只能全片渲染」—— 用实际调用证明，**不是**断言某个文件不存在
  （断言不存在的文件在本项目吃过亏：`assert "mkdtemp" in source` 匹配到了解释该 bug 的注释）。
- 「单帧渲染可用」—— `still.mjs` 是真实存在的入口，可以实测。

**至少两条变异，各贴 `-rf` 原始输出**：

| 变异 | 期望 |
|---|---|
| 让 `render.mjs` 接受一个不存在的 `--comp` | 守卫红（若它断言"非法 comp 必须失败"） |
| 让 `still.mjs` 对越界 `--frame` 静默返回 | 守卫红（若它断言"越界必须报错"） |
